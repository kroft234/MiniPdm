# Mini-PDM — хранение конструкторской документации

Упрощённая система мини-PDM: импорт данных из экспорта JSON, нормализация
до плоских моделей, хранение в SQLite, просмотр дерева состава, спецификации,
расчёта массы, циклов, версионирование и жизненный цикл объектов.
Интерфейс — WPF (MVVM).

---

## Сборка и запуск

Требуется [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0).
Никакой дополнительной настройки не нужно: пакеты NuGet подтягиваются
автоматически при первом `dotnet build`.

```bash
# сборка всего решения
dotnet build MiniPdm.sln

# тесты (117 шт.)
dotnet test MiniPdm.sln

# графический интерфейс (WPF)
dotnet run --project src/MiniPdm.Wpf
```

Путь к базе задаётся переменной окружения `MINIPDM_DB`; по умолчанию файл
`minipdm.db` создаётся рядом с программой.

### Импорт в интерфейсе

1. Запустите `dotnet run --project src/MiniPdm.Wpf`.
2. Нажмите **Импорт папки…** и выберите `cad-export/cad-export` (исходный экспорт).
3. После импорта появятся 38 объектов; откройте `РДЦЛ.304112.300` — дерево,
   спецификация, масса и версии рассчитаются автоматически.
4. Повторный импорт той же папки — «без изменений»; далее можно импортировать
   `cad-export-v2` — появятся новые версии изменившихся объектов.

## СУБД и схема

**SQLite** (`Microsoft.Data.Sqlite`, файл-база): не требует сервера и настройки —
`dotnet build` + `dotnet run` и всё работает.

Схема — один файл **`src/MiniPdm.Data/Sqlite/schema.sql`**, встроенный в сборку
как embedded resource и выполняющийся при старте (`SchemaInitializer` — прогоняет
скрипт, если таблиц ещё нет). Миграций нет: схема создаётся заново, если файла
базы нет. Реализация хранилища — `SqlitePdmStore` за интерфейсом `IPdmStore`
(запросы собраны в `Sql.cs`, выполнение — через Dapper).

Таблицы:

```sql
pdm_object        -- объект: id, ключ, тип, обозначение, наименование, текущая версия
object_version    -- версия: состояние, материал, масса, ссылка на источник
bom_link          -- ребро состава: родитель, ребёнок, количество, типовой состав
import_log        -- журнал импорта: файл, результат, причина отклонения
```

Плюс индексы по типу/состоянию/связям и триггеры, поддерживающие поле
`current_version_id` в согласованном состоянии.

## Архитектура

Решение разбито на проекты с зависимостями только «вниз по слою»:

```
MiniPdm.Cli  ─┐
MiniPdm.Wpf  ─┼─> MiniPdm.Core <─ MiniPdm.Tests
              │        ▲
MiniPdm.Data ─┘        │
MiniPdm.Cad ───────────┘
```

| Проект | Что внутри |
|---|---|
| `MiniPdm.Core` | домен: `ObjectState`/`ObjectType`, правила жизненного цикла (`StateTransitions`), валидация импорта, парсер JSON-экспорта (`Cad`), импорт (`FolderImportService`, `VersionPlanner`), расчёты (`BomCalculator`, `CycleDetector`, `BomTreeBuilder`) |
| `MiniPdm.Cad` | чтение файлов араска: `JsonCadDocumentReader`, `FileSystemCadExportReader` |
| `MiniPdm.Data` | SQLite: `SqlitePdmStore`, `schema.sql`, `SchemaInitializer`, `Sql` |
| `MiniPdm.Cli` | консольная обёртка над теми же сервисами (`Program.cs`): импорт, дерево, спецификация, масса, утверждение версий |
| `MiniPdm.Wpf` | окно (XAML), `MainViewModel`, сервисы окон, композиция через Jab |
| `MiniPdm.Tests` | 117 тестов: домен, валидация, хранение, e2e-сценарий |

Проект `MiniPdm.Cli` в задании не требуется — это тонкая консольная обёртка
над теми же сервисами; её команды дают тот же результат, что и кнопки окна,
и именно ими получен вывод раздела «Отчёт об импорте».

Ключевые решения:

1. **Импорт — транзакция.** `FolderImportService` читает и валидирует все файлы
   в памяти, а записывает одной транзакцией SQLite: либо весь импорт, либо ничего.
   Отчёт (`ImportResult`) формируется независимо от успеха записи.
2. **Валидация до записи.** `ObjectSetValidator` проверяет целостность набора:
   ссылки на несуществующие файлы, латиницу в номере, дубликаты обозначений,
   циклы — до того, как появятся строки в базе.
3. **Версионирование.** `VersionPlanner` сравнивает принятые объекты с текущими:
   изменения содержимого → новая версия, без изменений → без новой версии.
   Утверждение/аннулирование — только через `StateTransitions`: одни и те же
   правила в любом месте программы.
4. **Плоские строки вместо графа.** `IPdmStore.GetBomTreeRowsAsync` отдаёт плоский
   список рёбер; `BomCalculator`/`CycleDetector` строят из него дерево,
   спецификацию, массу и циклы. Один источник данных — одно и то же число во
   всех представлениях.
5. **MVVM без логики в code-behind.** `MainWindow.xaml.cs` — один
   `InitializeComponent()`; всё состояние и команды в `MainViewModel`.
   Диалоги вынесены в `IDialogService` (тестируется заглушкой).
6. **Композиция через Jab** (`[ServiceProvider]`): DI-контейнер без рефлексии;
   одна точка композиции на приложение — `AppServices.cs`.

## Что не сделано / ограничения

### Не сделано: дополнительная часть задания

Обязательная часть выполнена полностью. Из восьми пунктов «будет плюсом»
выполнено использование стека (Dapper, Jab, xUnit); остальное:

- **Ленивая подгрузка узлов дерева** — дерево строится целиком одним
  рекурсивным запросом. Как бы сделали: при первом раскрытии узла запрашивать
  его детей отдельно (`Children == null` → подгрузка по требованию).
- **Отмена импорта** — асинхронность и индикатор прогресса есть
  (`FolderImportService.ProgressChanged`), а кнопки отмены нет: импорт
  запускается с `CancellationToken.None`. Как бы сделали: `CancellationTokenSource`
  на кнопке «Импорт папки…»; токен уже прокидывается в
  `FolderImportService.ImportAsync(folder, ct)` — менять только вызов в UI.
- **Поддержка двух СУБД (PostgreSQL и MS SQL)** — работает только SQLite.
  Как бы сделали: все запросы уже собраны в одном месте (`Sql.cs`) — добавить
  туда диалект PostgreSQL и выбор провайдера в конфигурации приложения.
- **docker-compose.yml** — отсутствует: SQLite хранится файлом, серверный
  контейнер не нужен; для PostgreSQL потребовался бы сервис в compose.
- **Экспорт сводной спецификации в CSV/XLSX** — нет. Как бы сделали: кнопка
  рядом со спецификацией, данные уже готовы в `SpecificationItemViewModel`.
- **Сравнение двух версий сборки** — нет. Как бы сделали: запрос двух срезов
  `bom_link` на указанные версии и диф по парам «объект → количество».
- **Структурированное логирование (Serilog)** — нет: статусы пишутся через
  `Console.WriteLine` и показываются в окне отчёта.

### Принятые ограничения

- **Нет миграций схемы** — схема только создаётся (`schema.sql`), версионирования
  структуры нет: для мини-PDM считается избыточным.
- **Один пользователь** — авторизации и параллельного доступа нескольких
  конструкторов нет.
- **Нет экспорта обратно** в формат CAD (задание не требует) и нет прикрепления
  файлов чертежей к версиям.
- **Колонка «Создана» в таблице версий** не показана в UI: в доменной модели
  `StoredVersion` дату создания не несёт (поле есть в схеме, извлекается при
  записи) — если понадобится, вывод делается за счёт расширения модели.
- **Расчёт массы** использует текущие (последние неаннулированные) версии
  компонентов; масса сборки не хранится, а считается на лету.
- Единственные «цветные» замечания сборки — предупреждения CS8602/CS4014 в
  тестах (не влияют на результат).
